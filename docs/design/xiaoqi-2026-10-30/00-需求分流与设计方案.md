## 0. 一句话结论

产品方「后端要从 0 实现」的前提不成立。**v1.0 要验收的 15 个工具 + 2 个工作流 + 本地生活只读 + 历史回填 + 资产列表 + 模型价目 + 上传，Java 主项目的 creaft v1 兼容层全部已有**，前端把 4 个 API 文件改成适配层即可接通，Java 只改配置和两行常量。

本项目（Go）真正要新开的，只有主项目确实没有的四块：

| 优先 | 模块 | 为什么主项目没有 |
|---|---|---|
| P0 | **商拍换装 / 姿态复刻 s1.1 新链路**（切图 → 反推 → 生图） | Java 的 `ai-model-tryon` 是 1 件衣服 + 1 模特的老接口；s1.1 的 9 张服装分件分角度、按件面料、DeepSeek 反推、姿势逐张提示词，Java 完全没有 |
| P1 | **资产库增强**（模特/场景/妆容/发型/配饰分类 + 计数 + 资产级收藏 + 标签字典 + 版本 + 关系） | Java 资产按入口码分类、只有任务级收藏、无版本/关系表 |
| P2 | **画布**（画布文档存取、单节点执行、候选结果、模板） | 任何仓库都没有用户画布的 nodes/edges 存储；Java 只有画布上的 4 个 AI 操作 |
| P2 | **用户提示词库**（官方 19 条 + 我的） | Java 只有管理端 Prompt Lab 和只读模板 |

另外两项**不建议在 Go 做**，理由见 §3：统一契约层（`/meta`、`POST /tasks`、`/history` 游标）放前端适配；图片工具「四档模型」需要产品先拍板。

## 1. 必须先知道的 5 个事实

这些事实改变了需求包里的多处假设，设计建立在它们之上。

### 1.1 Java 已经有一整套 creaft v1 兼容接口，覆盖契约全部 32 条

`fusion-aigc/contracts/user-api-compat-v1/manifest.json` 118 条 creaft_v1 路由。17 个工具逐条对上（`POST /api/v1/tools/ai-*`），14 个工作流模板全在 `afv_compat_workflow_template`（`/workflows/fashion|visual|video` + title），本地生活的品牌档案、模板、`/workflows/local-life` 也在兼容层里。历史接口 `GET /api/v1/{tools|workflows}/{title}/histories` 的 payload 里带 `request` 完整快照和 `inputRoles`，**可回填**。模型价目 `/api/v1/features/{image-model-configs,video-model-configs,biz-points}` 按用户实时报价，原型的 `api/model-configs.ts` 本来打的就是这三条。

对照明细见 `08-Java主项目能力盘点.md`。

### 1.2 原型要并入的「宿主」是桌面 Electron 客户端，不是 fusion-aigc-web

原型文档 `refs/前端接入边界-2026-10-24.md` 写明线上壳是 `_rea-shell/out/renderer` 的 `AppLayout + NMenu`。本机的 `fusion-aigc-web` 是另一套网页前端（Vue3 + Naive UI，首页/图片/视频/电商 14 页/资产），**一条 creaft v1 兼容接口都没调**，只用 Java 原生 `/api/v1/creation/*`。「只改前端」落在哪个仓库，需要你拍板（§7 第 1 条）。详见 `06-线上前端fusion-aigc-web盘点.md`。

### 1.3 落点只有两个仓库：fusion-aigc（Java，只维护）与 fusion_aigc_go（本项目，新功能）

所有「Java 没有」的功能一律落本项目。

### 1.4 Go 侧没有 ai-gateway 客户端，gateway 也不认 Go 调用方

`pkg/aigc` 只封装 AIGC 执行面（`/aigc/generate`、`/aigc/getRes`，task_type 9/70/…/92），没有通用文生图、图生图、取消。`ai-gateway/contract/hmac.md:55-56` 只登记了 `fusion-java`、`fusion-java-admin` 两个调用方。**凡是需要「按模型生图」的新功能（商拍生图、姿态生图、画布节点），都先要在 ai-gateway 登记 `fusion-go` 调用方并写 Go 版 HMAC 客户端**。这是 P0 的跨团队前置项。

### 1.5 s1.1 后端包只交付了「反推提示词」这一步

两份 Python（`serve_reverse-2026-10-30.1.py` 商拍基线 3867 行、`.3.py` 姿态基线 2776 行）是纯标准库 HTTP 服务，唯一上游 DeepSeek（`deepseek-flash`，`chat/completions` + `image_url`）。切图执行、组图、生图、队列、计费、历史、资产、鉴权全要我们做。指南里的端到端骨架代码有 4 处 bug 不能照抄。详见 `02-s1.1-商拍姿态.md`。

## 3. 两个不建议在 Go 做的事

**统一契约层（BFF）。** 把 `/meta`、`/tasks`、`/history` 游标翻译到 Java 兼容路由，技术上可以在 Go 做（透传用户 Bearer，Go 能校验共用 Redis 会话），但它不是「主项目没有的功能」，只是换一层外壳，而且多一跳、多一处要维护的错误码映射。原型自己说「前端只认三样：接口 base、token、三条链路」且落点就是 4 个 API 文件，前端适配层是最短路径。只有当产品坚持并发 ≤4 和 429 限流时，才值得起 BFF。

**图片工具四档模型。** Java 兼容层的图片模型由能力绑定 `model_roles` 决定，请求里的 `model` 只被记进 params，不参与路由；只有视频走别名。结论（已定）：**14 个不露模型下拉的老工具走 Java、不选模型；唯一露出下拉的「图片生成」连同商拍、姿态、画布一起在 Go 的 gateway 生图链路里实现四档**，Java 不破冻结，Go 也不用重做 14 个工具。

## 4. Go 新开模块一：商拍换装 / 姿态复刻（P0）

### 4.1 边界

- 输入：s1.1 前端 payload（商拍 12 字段，姿态 7 字段，见 `03-s1.1-前端包.md` B 节）。
- 产出：每「模特 × 张数」/ 每「姿势」一张图，进任务中心、素材库、计费。
- 复用：Python 反推服务作**内部 sidecar**；media 服务做下载、压缩、裁图、组图；ai-gateway 做生图；本项目 pkg/billing、taskcenter、asset、storage 原样套用。

### 4.2 组件

```
前端 ──► gateway-api  /api/v1/local-life/tryon/*  /api/v1/local-life/pose/*
              │ zrpc
              ▼
         tryon-rpc (新, 9205)
          ├─ 收单/编号/校验 ──► media 服务 ingest/conform(≤1600px)/image/crop/image/grid
          ├─ 反推编排 ──────► prompt-reverse sidecar (Python, 127.0.0.1:8090)
          │                     crop-plan / crop-check / analyze-batch / pose/source / pose/prompt
          ├─ 生图 ──────────► ai-gateway  image.edit (新 Go 客户端, caller=fusion-go)
          ├─ Poller ────────► Storage.Transfer → Billing.Settle → CAS 终态 → Asset.InsertSet → TaskCenter.Sync
          └─ 计费 Hold/Settle/Fail/Renew（pkg/billing，biz_type=LOCALLIFE，入口码新建 2 个 offer）
```

**sidecar 处理**：以 `.1` 为基线并入 `.3` 的约 25 行姿态差异（表情指令、重试参数），删掉静态页面、`/api/billing`、`PRISM_EMBED` 和上游转发（它会把任意 `/api/reverse/*` 原样转到第三方 IP），只保留 6 个业务路由，只监听内网。DeepSeek Key 只放 sidecar 环境变量。提示词和清洗逻辑**不改**，用 `pose-tests/validate_prompts.py` 当黄金回归；商拍另建 3 组黄金样本。Go 重写估 4000–5000 行、3–4 周，不在本期。

### 4.3 数据表（`deploy/sql/Go_V1.0.21__tryon.sql`，MySQL，`COLLATE=utf8mb4_unicode_ci`）

| 表 | 用途 | 关键列 |
|---|---|---|
| `afv_tryon_batch` | 一次提交（商拍或姿态） | id, user_id, workspace_id, kind(tryon\|pose), request_id(`uk_user_request`), payload json（全量字段快照）, source_sha1（姿态人物图）, status, crop_plan json, crop_check json, selected_images json, created_at |
| `afv_tryon_task` | 一张图 | id, batch_id, model_index, shot_index / pose_index, task_id(`uk_task_id`, 前缀 `tyo`/`pse`), prompt_text(mediumtext), prompt_meta json, gateway_call_id, status, result_rid, result_url, error_reason, billing_request_id, started_at, finished_at |
| `afv_tryon_prompt_cache` | 批次内缓存 | batch_id, cache_key(model_sha1 或 pose_sha1), kind(analyze\|source\|prompt), payload json |

状态机（对齐验收 I）：`queued → cropping → prompting → generating → done | failed`，每步一行 JSON 日志（job_id/step/ms/images/crops/degraded/cost），不记 base64、Key、完整 prompt。

### 4.4 关键规则（全部来自 s1.1 验收必过项）

| 规则 | 实现 |
|---|---|
| 批次级缓存 | 切图每批一次；`analyze` 每个模特一次（同模特多张共用 prompt）；姿态 `source` 按人物图 sha1 一次。否则 9×9=81 任务会产生 300+ 次视觉调用 |
| 编号与顺序 | `g-<item>-<angle>-<seq>` / `m-<i>`；单品按 `items[]`，角度 `front→back→side→detail→flat→unknown`；`lengths/sleeves` 只认 `items` 里有的件 |
| crop-plan 分批 | 服务端只处理前 6 张，9 张要分两批调用；框 0–1 归一化、4% 内边距、短边 <256 放大（media image/crop + resize） |
| crop-check | 一次 ≤12，只删 `ok=false && confidence≥0.85`，失败不阻断 |
| 组图 | 主图 → 细节（按单品轮询，名额 `max(1, 9-主图-1)`）→ 模特 1 张最后；sha1 去重；总数 ≤9 |
| 生图 | 图 1 = 模特 / source，图 2..N = 服装细节 / poseImage；prompt 首行加图序声明，正文逐字不动；并发 3；只重试 429/5xx/超时 1.2/2.4/4.8s；幂等键 `batch_id:model:shot`；超时 300s |
| 模型映射 | 前端 通用/GPT/Banana/Seedream → gateway model group（img.gpt-image-2 / img.nano-banana-2.1 / img.seedream-5-pro；通用 = 后台配置默认）；分辨率大小写归一 |
| 计费 | 每个 `afv_tryon_task` 一张预留单，RequestID = `tryon-<task_id>`；Hold 在提交时，Settle 在转存成功后，Fail 退款；反推失败整批退；入口码两个新 offer 在 Java 后台配置，能力码复用 `ecom_image_gen` |
| 任务中心 | `taskcenter.Source{Table: afv_tryon_task, Prefix: "tyo"/"pse", Type: image, EntryCode: ...}`，`origin_service=LOCAL_LIFE`；admin-api `parseOriginRef` 支持新前缀 |
| 校验 | 服务端复查 9 张/6 角度/3 件互斥/模特 ≤9/姿势 ≤9；拒绝 `blob:` URL；`storage.Owned` 校验输入 URL |

## 9. 10-30 已定结论与数据层决定

### 9.1 前端归属

用户前端由另一位同事负责，**不归我们**；我们负责的前端只有管理后台 `fusion-aigc-admin`（它已有 `/local-life` 一组页面在调本项目 admin-api，`src/api/local-life-admin.ts`）。因此：

- 对用户前端的交付物是**接口文档**：`docs/api/api-studio.md`（商拍/姿态/图片生成）、`docs/api/api-asset-library.md`、v1.1 的 `api-canvas.md`。§2 里标「前端」的所有适配工作（schemaId → Java 兼容路由、错误码映射、OSS 直传）转交前端同事，我们只提供 §2.3 的对照表。
- 管理后台新增页面（本项目 admin-api + fusion-aigc-admin）：studio 任务列表 / 批次详情（切图框、组图、prompt、每步耗时与成本）/ 重做 / 强制失败 / sidecar 状态；资产扩展的分类与标签字典；v1.1 的画布官方模板、提示词库官方条目。

### 9.2 路由前缀：继续用 `/api/v1`，可行

nginx 现有规则是 `location ^~ /api/v1/local-life/admin` → Go admin、`location /api/v1/local-life` → Go gateway、其余 `/api/v1/` → Java（`deploy/server/nginx/aigc-local-life.conf.tmpl:35-50`）。nginx 最长前缀优先，只要新前缀**不与 Java 的 31 个一级前缀撞车**（已核对 Java 全部 `@RequestMapping("/api/v1/...")`：asset、tasks、tools、creation、features、models、users 等），各加一条 `location ^~` 即可，Java 零改动，Bearer token 两边共用。

| 模块 | 用户侧前缀（→ Go gateway-api） | 管理侧 |
|---|---|---|
| studio（商拍/姿态/图片生成） | `/api/v1/studio/*` | `/api/v1/studio/admin/*` |
| 资产库增强 | `/api/v1/asset-library/*`（Java 是 `/api/v1/asset`，不撞） | `/api/v1/asset-library/admin/*` |
| 画布（v1.1） | `/api/v1/canvas/*`（Java 画布操作在 `/api/v1/agent/canvas`，不撞） | `/api/v1/canvas/admin/*` |
| 提示词库（v1.1） | `/api/v1/prompt-library/*`（Java 是 `/api/v1/creation/prompts`） | `/api/v1/prompt-library/admin/*` |

管理侧与用户侧是两个进程（admin-api 8889 / gateway-api 8888），每个模块要**两条** location，`/admin` 的那条必须放在前面（与现有 `/api/v1/local-life/admin` 压在 `/api/v1/local-life` 之前同一套路）：

```nginx
location ^~ /api/v1/studio/admin { proxy_pass http://admin-api;   }
location ^~ /api/v1/studio       { proxy_pass http://gateway-api; }
```

4 个模块共 8 条，都放在 `location /api/v1/` 之前。Java 管理链是 `/api/v1/admin/**`，不撞；Java 后台向 Go 转发「重做 / 强制失败」仍走现有 local-life/admin 入口，靠 `origin_ref` 前缀分流，不受影响。admin-api 的 `admin.api` 为每个模块加一个新前缀的 `@server` 组；`mkconf`、`install.sh` 同步。

### 9.3 四档模型：图片生成进 Go

结论见 §3 与 §4.7：14 个不露模型下拉的老工具走 Java 不选模型；图片生成、商拍、姿态、画布四处需要选模型的，全部走 Go 的同一条 gateway 生图链路。Java 不动。

### 9.4 商拍/姿态：按 v1.0 + v1.1 功能合集做

即 §4 全部范围：s1.1 的切图 → 反推 → 生图完整链路、批次级缓存、计费、任务中心、资产入库、历史回填、管理后台、验收 A–J 全项。不再保留 `enabled:false` 的降级口径。

### 9.5 数据层：业务用 bun，计费/对账/定点审计用 sqlc（已定）

用户拍板：**新模块业务数据访问用 bun；计费、对账、定点审计类查询用 sqlc**（纯 SQL 文件，可审阅、可逐字核对）。老模块不动。可行性与约束：

| 项 | 结论 |
|---|---|
| 连接池 | 共用。go-zero v1.10.3 `sqlx.SqlConn.RawDB()` 取 `*sql.DB`，`bun.NewDB(rawDB, mysqldialect.New())`，不再开第二个池 |
| 方言 | `mysqldialect`；Upsert 写 `On("DUPLICATE KEY UPDATE").Set("x = VALUES(x)")`，草案里的 `ON CONFLICT … EXCLUDED` 是 PG 语法要改 |
| 可观测 | bun 路径脱离 go-zero sqlx 的慢日志/熔断/metrics，新模块统一挂一个 `bun.QueryHook` 把 SQL、耗时、错误接到 `logx`，慢阈值与 go-zero 默认 500ms 对齐 |
| 边界 | bun 只用于新表（`afv_studio_*`、`afv_asset_ext/version/relation/tag*`、`afv_canvas_*`、`afv_prompt_library_item`）；读 Java 表（`afv_asset`、`afv_creation_task` 等）也可经 bun 只读映射，但**写 Java 共享表仍走现有 pkg（billing、taskcenter、asset）**，不在 bun 里重写 |
| 状态迁移 | 保留 CAS 语义：`UPDATE … WHERE id=? AND status=?` 用 bun `Where` 显式写，按 `RowsAffected` 判断是否抢到 |
| 代码位置 | `pkg/bundb`（NewFromSqlConn、QueryHook、通用 Upsert 助手）；各模块 `app/<m>/model` 放 bun struct，不再用 goctl 生成；sqlc 产物在 `pkg/auditdb` |
| sqlc 的范围 | 只用于「钱」相关的只读/核对查询：studio 每批次/每任务的成本汇总（`cost_cny` 对 gateway `/v1/ledger/costs`）、预留单与任务终态一致性核对、`pkg/billing/audit.go` 风格的定点审计、后台对账报表。SQL 放 `db/audit/query/*.sql`，`sqlc.yaml` 在仓库根，生成到 `pkg/auditdb`；与 bun 共用同一个 `*sql.DB`。写操作一律不走 sqlc |
| 分工边界 | 一张表可以同时被 bun（业务读写）和 sqlc（审计只读）访问，但 sqlc 查询不得被业务逻辑调用，防止两处定义同一语义 |
