# 联盟用户注册 / 登录流程与写表梳理

> 用途：供 Go 重写登录注册服务参考。内容基于 `feat/reconcile` 分支当前代码（2026-09-23）。
> 关键源码：`UnionUserController`、`UnionUserAuthController`、`OpenAuthController`、`OpenUserController`、
> `UnionSignatureFilter`、`UnionIdentityServiceImpl`、`UnionTokenAuthService`、`UnionCredentialVerifierImpl`、
> `UnionIdempotencyServiceImpl`、`UnionAuthIdempotencyServiceImpl`、`UnionAuthAuditLogService`、
> `UserService`、`TeamService`、`TokenService`、`OpenAppKeyService`、`SecretEncryptor`、`GlobalExceptionHandler`。

## 一、入口总览

| # | 接口 | 鉴权链 | 调用方 | 作用 |
|---|---|---|---|---|
| A | `POST /api/v1/union/user-register` | 签名链 `UnionSignatureFilter` | 联盟服务端 | 注册，已存在就同步资料（upsert），**不发 Token** |
| B | `POST /api/v1/auth/union-token-login` | 用户链，免登录 | 前端带联盟临时 token | 回调联盟接口拿用户信息，注册或登录，发 Token |
| C | `POST /api/v1/auth/union-login` | 用户链，免登录 | 前端带 `loginTicket` | 校验 HMAC 票据，登录或建号，发 Token |
| D | `POST /api/v1/user/bind-union` | 用户链，需登录 | 已登录用户 | 本地账号绑定联盟账号 |
| E | `POST /api/v1/open/auth/login`、`POST /api/v1/open/users/register` | 签名链 | 开放平台三方应用 | 按 `(appKey, externalUserId)` 建号或登录，逻辑和 A 基本一样 |
| — | `GET /api/v1/union/user-info`、`GET /api/v1/union/user-exists` | 签名链 | 联盟服务端 | 只读 |

统一返回体：`{"code":0,"msg":"...","data":{...}}`，字段用驼峰命名。

## 二、签名链的前置层（A、E 两类）

所有 `/api/v1/open/**` 和 `/api/v1/union/**` 请求，进控制器之前都先过 `UnionSignatureFilter`：

1. **带 token 的请求直接拒**：带了 `Authorization` 头，或 query 里有 `token` / `access_token` / `accesstoken` / `authorization` 参数，返回 401。
2. **读请求头**：`X-Union-App-Key`、`X-Union-Timestamp`（秒）、`X-Union-Nonce`、`X-Union-Signature`、`X-Union-Key-Version`（可选）。
3. **查配置**：先读 `afv_open_app`（请求头里有 appKey 就按它查，没有就取 `is_builtin=1` 那一行），字段缺了再逐个回退到 `afv_system_config`：
   `union_signature_enabled`（默认 true）、`union_whitelist_enabled`（默认 false）、`union_whitelist_ips`、`union_trusted_proxies`、`union_app_key`。
4. **签名开关和白名单开关都关**：一律返回 401，不会放行。
5. **签名开着时**：
   - 四个必填头缺任何一个都返回 401。
   - 时间戳和当前时间相差不能超过 300 秒。
   - 查密钥：`afv_open_app` 要求 `status=1`，再查 `afv_open_app_secret`，按 `key_version` 取（请求头没带就用应用行上的 `key_version`）；已退役（RETIRED）的不能用，轮换中（ROTATING）但过了 `valid_until` 的也不能用。
   - 密钥解密：AES-256-GCM，密文格式是 `base64(12 字节 IV + 密文 + 128bit tag)`，解密钥匙取环境变量 `OPEN_APP_SECRET_ENCRYPT_KEY`（base64，对应 `app.security.secret-encrypt-key`）。
   - 待签名串：

     ```
     METHOD\nURI\n按字典序排好的query（按 & 拆开排序后再拼回）\nsha256hex(body)\ntimestamp\nnonce\nappKey
     ```

     用 HmacSHA256 算出小写 hex，按常量时间比较。
   - 白名单也开着时，签名通过后还要校验 IP（签名加白名单，两者都要满足）。只有直连方是受信代理时才解析 `X-Forwarded-For`，从右往左跳过受信代理，取第一个非受信 IP；支持 CIDR。
   - 防重放：Redis `SETNX fusion:union:nonce:{appKey}:{nonce}`，TTL 300 秒。
6. **只开白名单时**：免签名，但 IP 必须命中白名单，时间戳和 nonce 仍然必填；请求头带了 appKey 时必须和配置的 appKey 一致。
7. 通过后先**写 `afv_union_request_log`**：`status=PROCESSING`，带 `request_id`（`union-` 加 32 位 hex）、`request_path`、`app_key`、`request_digest`（body 的 sha256）、`request_body`。然后把 appKey、requestLogId 等放进请求上下文，进控制器。结束后按响应体里的 `code` / `msg` 回填 `response_code`、`response_body`、`status`（HTTP 小于 400 且 code 为 0 算 SUCCESS，否则 FAILED）、`error_message`、`response_time`。
8. 鉴权失败直接写 `{"code":401,"msg":"..."}`，HTTP 状态是 401 或 403（IP 不在白名单时为 403）。

## 三、各流程的步骤和写表

### A. 联盟注册 `/union/user-register`（upsert）

请求体：`unionUserId` 必填。以下都可选：`nickname`、`avatar`、`phone`、`birthday`（yyyy-MM-dd）、`gender`（0/1/2）、`province`、`city`、`realNameStatus`（none / pending / approved / rejected）、`roles`（不落库）、`status`（active / frozen / deactivating / deactivated）。

> 昵称、头像必须可选。上游用户没设头像很常见，这时硬性校验返回 400，会让上游发放点数的事务回滚并无限重投。

1. **幂等开始**，表 `afv_union_request_idempotency`：
   - 幂等键是 `union:{appKey}:register:{unionUserId}`，超过 128 字符直接报错。
   - 先按 key 查。查到且 `status=SUCCESS`，就把 `response_body` 原样返回；查到但不是 SUCCESS，照常重新执行。
   - 查不到就 INSERT：`request_log_id`、`idempotency_key`、`app_key`、`status=PROCESSING`、`expired_at=now+7天`。
2. 按 `union_user_id` 查 `afv_app_user`：
   - **已存在**：更新资料。入参为空的字段不覆盖；`nickname` 同时写 `nickname` 和 `union_nickname`，`avatar` 同时写 `avatar` 和 `union_avatar`；`phone`、`birthday`、`gender`、`province`、`city`、`real_name_status` 非空才写；`status` 映射成 0 或 1。执行 `UPDATE afv_app_user`。
   - **不存在**：走 `createUnionUserWithProfile`（appKey 取签名上下文），见第四节，写 `afv_app_user`、`afv_team`、`afv_team_member`。
3. 幂等收尾：UPDATE 幂等记录，写入 `status=SUCCESS`、`response_code`、`response_body`（整个 CommonResult 的 JSON）和它的 sha256（`response_body_hash`）。
4. 返回 `UnionUserInfoRespVO`：

   | 字段 | 说明 |
   |---|---|
   | `userId` | 本地用户 ID |
   | `avatar`、`nickname` | |
   | `phone` | 脱敏，形如 `138****1234`（长度小于 7 原样返回） |
   | `birthday`、`gender`、`province`、`city`、`realNameStatus` | |
   | `roles` | 固定是空数组 |
   | `status` | 只会是 `active`（status=1）或 `frozen` |
   | `createdAt` | ISO_LOCAL_DATE_TIME |

开放平台的注册 `/open/users/register` 流程相同，区别只有三点：幂等键前缀是 `open:`，按 `(source_app_key, external_user_id)` 查人，建号走 `createAppUser`（建完再按同样的“空值不覆盖”规则补齐资料字段）。

### B. 临时 Token 登录 `/auth/union-token-login`

请求体：`{"token": "..."}`。这条**没有幂等，也没有审计表**。

1. 拼上游地址，按优先级取：
   1. 内置应用行（`afv_open_app.is_builtin=1`）的 `token_url`；
   2. `afv_system_config.union_token_url`；
   3. 内置行的 `base_url`；
   4. `afv_system_config.union_base_url`；
   5. yaml 里的 `app.union.base-url`。

   `token_url` 含 `{token}` 占位符就直接替换；其余情况都拼成 `{base 去掉尾部斜杠}/api/v1/auth/{token}/user`。
2. 发 `GET` 请求，响应格式是 `{code, message, data}`，**`code==1` 才算成功**。
   - 请求失败或返回空：报第三方错误。
   - `code != 1` 或 `data` 为空：报参数无效（默认提示“Token无效或已过期”）。
   - `data` 字段：`userId`（long）、`nickname`、`avatar`、`phone`、`birthday`、`gender`（long）、`province`、`city`、`realNameStatus`、`status`、`roles`、`createdAt`。
3. `userId` 为 0 视为无效。按 `union_user_id` 查本地用户：
   - 不存在：走 `createUnionUserWithProfile`，`appKey` 传 null，最后归属到内置联盟应用。
   - 存在：更新资料。注意这里和 A 的口径**不一致**：`gender`、`union_nickname`、`union_avatar` 无条件覆盖，上游传空也会写成空；其余字段非空才写。
4. `status != 1` 返回 2007 账号已禁用。
5. 发 Token，见第五节。

### C. 票据登录 `/auth/union-login`

请求体：`{"loginTicket": "..."}`，请求头 `Idempotency-Key`。

1. **`Idempotency-Key` 请求头**：注解上写的是可选，但 `begin` 里遇到空值会报“不能为空”，所以**实际上是必填**，最长 128 字符。
2. **幂等**，表 `afv_union_auth_request_log`：
   - `action = union.login`，`subject_id = "anon"`。
   - `idempotency_key_hash = sha256("union-auth:union.login:anon:" + key)`。
   - `request_digest` 算法：

     ```
     sha256("action=11:union.login;credentialDigest=64:" + sha256hex(ticket) + ";")
     ```

     每个字段拼成 `name=长度:值;`。
   - 按 `(action, subject_id, idempotency_key_hash)` 查到同一个 key 时：
     - digest 不一致：把状态改成 CONFLICT，报 46009；
     - 已过期：报 46012；
     - 还在 PROCESSING：报 46011；
     - FAILED：按记录里的错误码和信息重新抛出；
     - 否则重放：按记录里的 `user_id` 重新签一次 Token（用户必须仍为启用状态）。
   - 查不到就 INSERT 一条 PROCESSING（`expired_at=now+7天`），撞唯一键时回查，再走上面的判断。
3. **验票据**：
   - `loginTicket` 先尝试 base64url 解码，失败就当明文，然后按 `k=v&k=v` 解析。
   - 必填字段：`purpose=login`、`unionUserId`、`expiresAt`（毫秒时间戳）、`nonce`、`signature`；缺字段报 40001，过期报 40002。
   - 待签名串：

     ```
     purpose={purpose}&unionUserId={unionUserId}&expiresAt={expiresAt}&nonce={nonce}[&nickname={nickname}][&avatar={avatar}]
     ```

     `nickname` 和 `avatar` 存在时依次追加。
   - 用 HmacSHA256 算小写 hex，常量时间比较。**密钥是 `afv_system_config.union_app_secret`**，全局唯一一把，不按应用区分；没配置报配置错误。
   - nonce 一次性：Redis `SETNX fusion:union:credential:login:{nonce}`，TTL 取到 `expiresAt` 为止（最少 1 秒）。已经用过的 nonce 不直接报错，而是标记为 `replayed=true` 交给后续判断。
   - `credentialHash = hmacHex(secret, "login:{unionUserId}:{expiresAt}:{nonce}")`。
   - `nonceHash = hmacHex(secret, "login:{nonce}")`。
4. 按 `union_user_id` 查用户：
   - **存在**：如果是重放，但 `afv_union_auth_audit_log` 里没有 `action=union.login`、`status=SUCCESS`、这个 `credential_hash` 的记录，写审计 FAILED 并报 40002。然后检查启用状态（未启用报 2007），写审计：重放写 REPLAY，否则写 SUCCESS。
   - **不存在**：如果是重放，写审计 FAILED 并报 40002。否则调 `createUnionUser` 建号。票据里其实没有 appKey，所以**永远归属内置应用**。然后写审计 SUCCESS。
5. **审计表** `afv_union_auth_audit_log` 用**独立事务**写（`REQUIRES_NEW`），业务回滚时审计仍然保留。写入字段：`action`、`status`（SUCCESS / REPLAY / FAILED）、`user_id`、`union_user_id`、`credential_hash`、`nonce_hash`、`request_id`（取 nonceHash，截到 128）、`error_code`、`error_message`（截到 512）。
6. 成功时把幂等记录 UPDATE 成 SUCCESS，带上 `user_id`、`union_user_id`、`credential_hash`、`nonce_hash`、`response_code=0`；失败时 UPDATE 成 FAILED，带错误码和错误信息。最后发 Token。

### D. 绑定 `/user/bind-union`

请求体：`bindToken`、`unionUserId`，请求头 `Idempotency-Key`，需要用户已登录。

结构和 C 相同：`purpose=bind`，`action=union.bind`，`subject_id = "user:{userId}"`；`request_digest` 由 `action`、`userId`、`unionUserId`、`credentialDigest` 四个字段拼成；票据里的 `unionUserId` 必须和请求体里的一致。分支判断：

- 当前用户已绑定：
  - 绑的正是这个联盟账号：幂等成功（重放时同样要求审计表里有该凭证的 SUCCESS 记录）；
  - 绑的是别的联盟账号：报 40010。
- 这个联盟账号已被别人绑定：报 40012。
- 重放凭证且没有成功绑定记录：报 40002。
- 否则走 `markUnionBound`，UPDATE `afv_app_user`：`union_user_id`、`login_source=UNION`、`union_bound=1`、`union_bound_time=now`、`data_source=2`、`union_nickname`、`union_avatar`；`nickname` 和 `avatar` 非空时也一起覆盖。然后写审计 SUCCESS。

### E. 开放平台登录 `/open/auth/login`

请求体：`externalUserId`（必填）、`nickname`、`avatar`。

`appKey` 取签名上下文里的值，不从请求体读。按 `(source_app_key, external_user_id)` 查，查不到就调 `createAppUser`；状态不为 1 报 2007；然后发 Token。没有幂等表，靠用户表的唯一键兜底。

## 四、建号写表（共用部分）

### `afv_app_user`：三种建号方法的取值

| 字段 | createUnionUser（C） | createUnionUserWithProfile（A / B） | createAppUser（E） |
|---|---|---|---|
| username | `union_{unionUserId}` | `union_{unionUserId}` | `app_{appKey后8位}_{extId}` |
| password | BCrypt(随机 UUID)，不可用于登录 | 同左 | 同左 |
| nickname | 入参，为 null 时 `联盟用户{id}` | 入参，为空时 `用户{id}` | 入参，为 null 时 `用户{id}` |
| avatar | 入参 | 入参 | 入参 |
| phone / birthday / province / city | — | 入参 | 建号后按资料补写 |
| gender | 列默认 0 | 入参，缺省 0 | 列默认 0 |
| real_name_status | 列默认 `none` | 入参，缺省 `none` | 列默认 `none` |
| source_app_key | 显式 appKey，没有就取内置应用 app_key，再没有就 NULL（打 WARN） | 同左 | appKey |
| external_user_id | = unionUserId | = unionUserId | extId |
| union_user_id | unionUserId | unionUserId | NULL |
| login_source | UNION | UNION | OPEN |
| union_bound / union_bound_time | 1 / now | 1 / now | 列默认 0 / NULL |
| data_source | 2 | 2 | 2 |
| union_nickname / union_avatar | 入参原值，可能为 null | 入参原值 | — |
| status | 1 | 按 status 映射：frozen / deactivating / deactivated → 0，其余 → 1 | 1 |

- 唯一键有两个：`username`，以及 `uk_app_external_user (source_app_key, external_user_id)`。
  - `external_user_id` 和 `union_user_id` 必须一起填，否则另一列是 NULL，MySQL 唯一索引允许多行 NULL，约束就等于没有。
- 撞唯一键时回查已有记录并返回：联盟建号按 `union_user_id` 回查，开放平台建号按 `(appKey, extId)` 回查。**撞键这条路径不建团队。**

### 建号成功后建团队

1. INSERT `afv_team`：`name` 取昵称，`owner_user_id` 是新用户，`status=1`。
2. INSERT `afv_team_member`：`team_id`、`user_id`、`role=1`（拥有者），`status=1`。

`currentTeamId` 的取法：取该用户 `afv_team_member` 里 `status=1` 的记录，按 `team_id` 升序、再按 `id` 升序，取第一条。

## 五、发 Token（Redis，不写库）

A 不发 Token，B、C、E 发。Token 是去掉横线的 UUID（32 位 hex）。

| Key | Value | TTL |
|---|---|---|
| `fusion:token:{access}` | `{"userId","username","currentTeamId","issuedAt"}`，`issuedAt` 为 epoch 秒 | `TOKEN_ACCESS_HOURS`，默认 2 小时 |
| `fusion:refresh_token:{refresh}` | 同上 | `TOKEN_REFRESH_DAYS`，默认 7 天 |
| `fusion:token:{access}:refresh` | refresh | refresh 周期（默认 7 天） |
| `fusion:refresh_access:{refresh}` | access | refresh 周期 |
| `fusion:user_sessions:{userId}` | ZSET，member 是 access，score 是当前秒 | refresh 周期 |

登记会话时，先剪掉 score 早于“当前时间减 refresh 周期”的成员；再按 `max-concurrent-sessions`（默认 0，表示不限）淘汰最久没刷新的会话（淘汰时删除该会话的全部 key）。允许多端同时在线，登录不会踢掉旧会话。

返回 `LoginRespVO`：`accessToken`、`refreshToken`、`expiresIn`（秒）、`refreshExpiresIn`（秒）、`userId`、`username`、`nickname`。

响应头：`Cache-Control: no-store`、`Pragma: no-cache`、`Referrer-Policy: no-referrer`。B、C、E 都有接口级限流，60 秒内最多 10 次。

**Go 服务和 Java 共存期间**，Java 的 `TokenAuthenticationFilter` 还在读这些 key，所以 key 名和 JSON 结构必须一模一样。

## 七、错误码与 HTTP 状态

| 错误码 | 含义 |
|---|---|
| 2007 | 账号已禁用 / 用户不可用 |
| 40001 | 联盟登录凭证无效 |
| 40002 | 联盟凭证已失效（过期或重放） |
| 40010 | 已绑定联盟账号 |
| 40011 | 联盟绑定凭证无效 |
| 40012 | 联盟账号已绑定其他用户 |
| 46009 | Idempotency-Key 已用于不同请求 |
| 46011 | 请求处理中，请稍后重试 |
| 46012 | 幂等请求已过期 |

Java 这边的 HTTP 状态映射规则（`GlobalExceptionHandler`）：

- 业务码是 400 / 401 / 403 / 404 / 409 / 500 时直接用作 HTTP 状态；
- 5xxx 返回 500；
- 其他业务码都返回 HTTP 200，靠 `code != 0` 表示失败；
- 参数校验失败返回 400；
- 撞唯一键（DuplicateKey）没有专门处理，会落到兜底，返回 500。

## 八、Go 重写要注意的地方

1. **有几张表的迁移脚本和代码对不上，先去真实库确认。** 迁移 `V1.0.1__init_schema.sql` 里：
   - `afv_union_auth_request_log` 没有 `request_digest`、`nonce_hash`、`response_code` 这几列，`user_id` 是 NOT NULL，但代码插入时不带 `user_id`；
   - `afv_union_auth_audit_log` 也没有 `credential_hash`、`nonce_hash`、`request_id`、`error_code`。

   照迁移建出来的库，C、D 两条流程应该会在 SQL 层报错。请在各个环境上执行 `SHOW CREATE TABLE`，以线上实际结构为准。
2. **HTTP 状态码决定上游会不会重试。** 上游会把 4xx 当成永久失败，不再重试；5xx 和“HTTP 200 + code != 0”当成可重试。所以 A 注册时，nickname、avatar 为空**绝不能返回 400**；并发撞键这类“重试就能成功”的情况也不能返回 4xx。详见 `docs/union/幂等与重试契约.md`。
3. **A 的幂等键没有包含请求体摘要。** 同一个 `unionUserId` 第一次成功后，之后的资料更新都会被原样重放，资料实际上停在第一次的状态。另外幂等表是先 select 再 insert，并发时撞唯一键会返回 500。建议 Go 版：
   - 把幂等键改成带上 body 的 sha256，同样的请求体重放，变了的请求体重新执行资料同步；
   - 撞键时用 `SELECT ... LIMIT 1 FOR UPDATE` 回查后重放（REPEATABLE READ 下普通读看不到对方刚提交的行）；
   - 超长的 key 折叠成哈希，而不是直接报错。
4. **幂等记录和业务不在同一个事务里。** 业务失败时记录会停在 PROCESSING，下次重试会重新执行（A 只重放 SUCCESS）。Go 版要保留“失败可重试”的语义。
5. **B 的资料同步口径和 A 不一致**：`gender`、`union_nickname`、`union_avatar` 在 B 里无条件覆盖。重写时建议统一成“空值不覆盖”，前提是和产品确认过。
6. **C 的票据密钥是全局的** `system_config.union_app_secret`，不是按应用区分；票据里也没有 appKey，建出来的号都归属内置应用。
7. **建号和建团队要在一个事务里**。撞唯一键回查成功的那条路径不建团队（已有用户本来就有团队）。
8. **两个共存期的坑**：
   - Java 对 `userByUsername` 有进程内 Caffeine 缓存，建号和改资料时会清缓存。Go 直接写 `afv_app_user` 时 Java 不知道，可能读到过期数据，要么避开，要么想办法通知失效。
   - 时间字段按 `Asia/Shanghai` 写入（Java 进程时区固定为 Asia/Shanghai）。
9. **登录时状态必须是 1。** 注册接口 A 不拦被冻结的用户，只在返回里标成 `frozen`。
10. **密码**：联盟和开放平台建出来的号，密码是随机 UUID 的 BCrypt，不能用密码登录；如果 Go 版要兼容本地密码登录，要用 BCrypt。
