## 2. 文档没写、但 Go 必须遵守的

### 2.1 冻结流水与批次明细要写全

Java 的确认、退款、部分结算都靠冻结流水找回批次（`BillingReservationServiceImpl.java:761-779`）：

1. 按**预留单的 `idempotency_key`** 找 `change_type='FREEZE'` 的那条 `afv_points_log`；
2. 再找它的 `afv_points_log_line`（每行带 `batch_id` 和数量）；
3. 缺任何一个直接抛错：「扣费单冻结流水不存在」/「扣费单冻结批次明细不存在」。

所以 **FREEZE 流水的幂等键必须等于预留单的幂等键**，并且要写 `afv_points_log_line`。正常情况下 Java 不会结算你们的单；但 3.2 说的运维动作一旦误点，这里不对就是报错或错账。

### 2.2 批次的退回与拆分规则

- **退款、取消、过期释放**：按 2.1 找到的冻结明细**退回原批次**，`remaining += x; frozen -= x`，并把批次状态**置回 `ACTIVE`，即使它已经是 `EXPIRED`**（`BillingReservationServiceImpl.java:744-746`）。之后由过期任务再把它过期掉。不是新建批次。
- **部分结算**：把冻结明细按批次 `expire_time` 升序排（空值视为最晚），从最早过期的批次扣掉实收，其余退回 `remaining`。扣完的批次置 `EXHAUSTED`，否则置 `ACTIVE`（`BillingReservationServiceImpl.java:335-361`）。
- **FIFO 可消费条件**完整写法是：`user_id=? AND status='ACTIVE' AND remaining>0 AND deleted=0`，排序键与你们文档一致，不带 `expire_time > NOW()`（`mapper/billing/PointsBatchMapper.java:14-24`）。

### 2.3 账户余额与批次剩余必须一致

批次过期任务直接按 `batch.remaining` 扣账户 `balance`。如果 Go 只改了账户、没同步改批次，或者反过来，过期时就会扣错数。

### 2.4 流水口径的补充

- 表里**没有 `balance_before` 列**。部分结算的 CONSUME 流水是 `balance_after = 结算前的 balance`，与你们写的一致。
- 释放类流水：目标状态是 `REFUNDED` 时记 `REFUND`，幂等键 `refunded:{no}`；目标是 `CANCELLED` / `EXPIRED` 时记 `UNFREEZE`，幂等键 `cancelled:{no}` / `expired:{no}`（`BillingReservationServiceImpl.java:458-472`）。
- `/api/v1/open/points/records` 按 `change_type` 推算「变更前点数」：`CONSUME` 视为余额不变，其余按 `amount` 反推。CONSUME 的口径不一致，这个接口的数就会错。

### 2.5 唯一键

- `afv_billing_reservation`：`uk_reservation_no`、`uk_idempotency_key`、`uk_biz(biz_type, biz_id)`。
- `afv_points_log`：`uk_ledger_no`、`uk_idempotency_key`。
- 两张表的幂等键都是**全表唯一**，列宽 `varchar(128)`；`biz_id` 是 `varchar(64)`，`biz_type` 是 `varchar(32)`。

### 2.6 毛利报表

Java 确认扣费时会写模型成本记录 `afv_model_cost_log`（`BillingReservationServiceImpl.java:164`），毛利报表（`controller/billing/AdminMarginController.java`）按已确认的预留单汇总收入、按成本记录汇总成本。

Go 不写成本记录的话，**本地生活的收入在毛利报表里是零成本，毛利虚高**。需要约定：要么 Go 也写成本记录，要么 Java 报表排除 `LOCALLIFE`。

其余报表（消耗、仪表盘、对账汇总）按 `change_type` 和日期聚合，不按 biz_type 分组，Go 的流水会直接并入总数；按 biz_type 字符串原样透传，不会因为不认识 `LOCALLIFE` 而报错。

## 3. 对你们第五节四个请求的回应

### 3.1 回收器跳过 `LOCALLIFE`：不只是日志噪音，优先级应为「高」

回收器每 60 秒按 `expire_time` 升序取 **100 条**（1.4）。未知 biz_type 的单不会被处理，**永远停在 HELD，每轮都会被重新选中**。

后果：只要 Go 有 100 条以上超时 30 分钟仍未收掉的单（比如你们的回收器宕了一段时间），Java 自己的超时单就**永远轮不到**，冻结点数不再自动回收。

照着旧的 `EXTERNAL_EXECUTION` 写法在分发里加一个跳过分支**解决不了**：跳过的单照样占那 100 个名额。正确做法是在查询条件里**只选 Java 拥有的 biz_type**（白名单）。**Java 侧已改**：回收查询加了 `biz_type IN (Java 枚举里的取值)`，你们的单不会再被选中、也不会再刷 WARN；后台「超龄占用扣费单」列表同样只列 Java 的单。

Go 侧也请保证：你们的回收器宕机期间，单子在恢复后能被收掉，不要长期停在 HELD。

### 3.2 运维动作对 `LOCALLIFE` 只读：优先级也应为「高」

`POST /api/v1/admin/billing/compensations/execute`（`service/billing/BillingCompensationServiceImpl.java`）只看状态、**完全不看 biz_type**：

| 动作 | 允许的状态 | 对 Go 的单的后果 |
| --- | --- | --- |
| `REFUND` | `HELD` / `SETTLEMENT_FAILED` / `BILLING_PENDING_REVIEW` | **Go 还在跑的单会被 Java 直接退款**，Go 之后再确认就是错账 |
| `RETRY` | `SETTLEMENT_FAILED` / `BILLING_PENDING_REVIEW` | Java 按自己的口径确认你们的单 |
| `IGNORE` | 同上 | 改状态为 `IGNORED`，不记流水 |

`/api/v1/admin/billing/exceptions/aged-held-reservations/recover` 走的是 3.1 的回收逻辑，对 `LOCALLIFE` 只打日志、不动账，没有问题。

**Java 侧已改**：补偿服务对非 Java biz_type 的单一律拒绝（`code=2005 ACCESS_DENIED`，提示「该扣费单属于其他服务（LOCALLIFE），请联系对应负责人处理」），不执行、不落补偿日志。

## 4. Java 侧已修复的问题

以下改动都在 fusion-aigc，与 Go 无关，但都作用在共享表上，告知你们一声。

### 4.1 批次过期任务的事务与锁

`service/billing/PointsBatchExpiryScheduledTask.java`：

- **原问题**：`@Transactional` 标在同类内部调用的方法上，事务没开，账户的 `FOR UPDATE` 语句结束就释放；批次不加锁，拿扫描时读到的旧行整行写回（连 `frozen` 一起）。同一批次上有并发冻结或退回时（Java 或 Go 都可能），账户可能按旧的 `remaining` 被多扣，批次 `frozen` 被旧值覆盖。
- **现在**：每个批次一个事务，**先锁账户、再锁批次**（与全局顺序一致），用锁后重读的值计算；锁后发现批次已不是 `ACTIVE` 或未到期就跳过。

### 4.2 生效时间为空的计价规则不被加载

`PricingRuleEngine.java` 改为「生效时间为空 = 发布即生效」，影响见 1.3。

### 4.3 退款重新激活的批次再次过期时没扣账户

2.2 里说过：退款会把冻结在已过期批次上的点数退回 `remaining`、置回 `ACTIVE`、加回账户余额，等过期任务再过期一次。原来过期任务看到 `batch-expire:{id}` 流水已存在，就只清零批次、不扣账户——**退回的点数在账户上凭空留下，余额与批次对不上**。

现在再次过期会正常扣账户，流水幂等键改为 `batch-expire:{id}:{uuid}`。**Go 侧如果也有批次过期逻辑，请注意同一批次可能过期不止一次。**

### 4.4 提交幂等键超长

创作提交的幂等键原来超过 191 字符才折叠成哈希，但预扣单的 `idempotency_key` 只有 128，129~191 字符的键会在预扣时插入失败。现在按 128 折叠。

## 5. 本地生活：两条平行线

Java 现有的本地生活和 Go 的本地生活是**两条平行线**：各自提交、各自计费、各自推到终态，互不调用，也不处理对方的单。

| | Java 本地生活 | Go 本地生活（aigc-local-life） |
| --- | --- | --- |
| 预扣单 `biz_type` | `CREATION` | `LOCALLIFE` |
| 冻结幂等键前缀 | `locallife:` | `golife:` |
| 任务落在 | `afv_creation_task` | Go 自己的表 |
| 超时回收 | Java 回收器 | Go 回收器 |
| 共享的 | 点数账户、批次、流水（按第 2 节的规则写） | 同左 |

两条线要保持平行，有两处容易交叉，请注意：

1. **offer 配置是共享的。** Java 的本地生活按入口码（`afv_billing_offer.entry_code`）找 offer 来报价和预扣。Go 的 offer 如果也放在这张表里并启用，它们会出现在 Java 侧的入口列表里（任务中心筛选、素材库分类、管理后台），Java 的本地生活提交接口也可能接受这些入口码、按 `CREATION` 计费，**一个入口两边都能提交**。请把 Go 专用 offer 的清单给我们（第 7 节第 2 条），Java 侧据此把它们排除在自己的入口之外。
2. **入口码不要复用。** Go 的入口码不要和 Java 已有的入口码同名，否则任务中心、素材库、管理后台的按入口统计会把两边混在一起。

## 6. 架构层面的意见

这个方案让 Go 直接写 Java 的账本表。Java 账本的任何细节变化，比如锁顺序、流水口径、批次退回规则、新增状态、列宽，都要和 Go 同步改。这份 9 月 27 日的文档到今天已有 6 处和代码对不上，说明这种约定会持续漂移，而且漂移不会报错，只会算错账。

如果短期按共享库方案走，建议至少做到两点：

1. **把第四节的三条硬约束和本文第 2 节写成账本场景用例**：冻结、全额确认、部分结算、退款、过期释放、批次过期，两边各自对共享库跑，结果按同一份期望值校验。
2. **Java 账本有改动时通知 Go**：涉及上述表的迁移和 `BillingReservationServiceImpl` 的改动，提交前同步给你们。

「账务是否需要单一负责方」由双方负责人另行决定；你们第六节已经按可替换为 HTTP 调用的形状设计，这一点很好。
