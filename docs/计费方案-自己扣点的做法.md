# 如果扣费走我们自己：怎么做

> 2026-09-27 · 对应《计费方案-扣点与入口码》第四节的方案 B。
> 下面每条都对着 `fusion_aigc` 的真实表和真实数据核过（1219 条预留单、2555 条流水），
> 不是照着猜的。

## 零、一句话方案

**价格照问 Java，账务动作我们写。**

不重新实现算价——`POST /api/v1/billing/quote/preview` 是配置驱动的，重写一份迟早分叉。
我们只做三个动作：冻结 / 确认 / 退回，直接写他们那批表。

## 一、账本语义（从真实数据核出来的）

一次完整的冻结→确认，`afv_points_log` 里是两行：

| change_type | amount | balance_after | frozen_after |
|---|---|---|---|
| FREEZE | **-70** | 6522 | **70** |
| CONSUME | **-70** | 6522 | **0** |

读法：
- **FREEZE**：余额 → 冻结。`balance -= P`、`frozen += P`，`amount` 记 `-P`。
- **CONSUME**：钱真正离开。只清冻结（`frozen -= P`），**余额不再动**（`balance_after` 和上一行一样）。
- **REFUND**：`frozen -= P`、`balance += P`，`amount` 记 `+P`。实例：`FREEZE -3 → REFUND +3`。

全库配平：`FREEZE 8988 = CONSUME 7894 + REFUND 1094`。✅

## 二、编号与幂等键的格式（照抄，别自创）

| 字段 | 格式 | 真实样例 |
|---|---|---|
| `reservation_no` | `BR` + 32 位 hex | `BRaf69b54b3fb84297b720a8493d239db5` |
| `ledger_no` | `PL` + 32 位 hex | `PLbba57b68e6a7439586447866fb07cab3` |
| `biz_type` | 固定 `CREATION` | — |
| `biz_id` | `{userId}_{requestId}` | `23_dd08c57033a24754becf80b990d9f96a` |

幂等键：

| 动作 | 他们用的 | 我们用 |
|---|---|---|
| FREEZE | `doubao:{bizId}` / `user:{uid}:creation:{uuid}` / `ecommerce-group:{bizId}` | **`golife:{bizId}`** |
| CONSUME | `confirm:{reservationNo}` | 一样 |
| REFUND | `refunded:{reservationNo}` | 一样 |

⚠️ **冻结那把键故意用自己的前缀 `golife:`**：他们本来就有三种前缀，再加一种不冲突；
而且运维一眼能看出哪些单是 Go 写的，出问题能划清。确认/退回那两把和他们保持一致——
它们以 `reservation_no` 为准，本来就唯一。

## 三、数据库替我们挡住的（这是方案 B 可行的根据）

这批表的约束比想象中严，很多"写错账"的情况根本写不进去：

```sql
afv_billing_reservation   UNIQUE uk_biz (biz_type, biz_id)        -- 同一次提交只能有一张单
                          UNIQUE uk_idempotency_key
afv_points_log            UNIQUE uk_ledger_no / uk_idempotency_key
afv_points_account        CHECK (balance >= 0 AND frozen_balance >= 0)
                          version                                  -- 乐观锁
afv_points_batch          CHECK (remaining + frozen <= amount)
                          CHECK (amount/remaining/frozen >= 0)
```

所以**重复提交靠 1062 冲突挡**（不是靠我们查一遍再写），**余额写穿靠 CHECK 挡**。
我们要做的是把冲突翻译成"幂等返回原单"，而不是报错。

## 四、三个动作的写法

### 冻结（提交生成时）

```
BEGIN
  1. INSERT afv_billing_reservation
       status='HELD'  biz_type='CREATION'  biz_id={userId}_{requestId}
       idempotency_key='golife:'+bizId     reservation_no='BR'+hex32
       feature_code / model_id / pricing_id / price_points / price_snapshot(quote 的返回)
       expire_time = NOW() + 按任务类型（见第五节）
     ── 撞 1062：说明是重试，读出原单原样返回，不再往下走

  2. 批次 FIFO 取钱（先过期的先用）
     SELECT id, remaining FROM afv_points_batch
      WHERE user_id=? AND status='ACTIVE' AND remaining>0
        AND (expire_time IS NULL OR expire_time>NOW())
      ORDER BY (expire_time IS NULL), expire_time, id
      FOR UPDATE
     逐批：remaining -= x, frozen += x

  3. UPDATE afv_points_account
        SET balance=balance-P, frozen_balance=frozen_balance+P, version=version+1
      WHERE user_id=? AND version=? AND balance>=P
     ── 影响行数 0 → 要么并发（重读重试，最多 3 次），要么余额不足（回滚，返回 1008）

  4. INSERT afv_points_log     change_type='FREEZE' amount=-P
                               balance_after / frozen_after 取第 3 步之后的值
  5. INSERT afv_points_log_line          每个动过的批次一行（before/after remaining+frozen）
  6. INSERT afv_billing_reservation_line 每个计费步骤一行（reserved_points, status='HELD'）
COMMIT
```

### 确认（生成成功，支持部分成功）

实际用量可能小于冻结量（多图部分失败）。差额当场退回，不留尾巴：

```
BEGIN
  reservation: HELD → CONFIRMED, confirmed_time=NOW()
  批次：确认的部分 frozen -= 实际（钱消失，不回 remaining）
        差额部分   frozen -= 差额, remaining += 差额
  account: frozen_balance -= P, total_consumed += 实际
           若有差额 balance += 差额, total_refunded += 差额
  points_log: CONSUME amount=-实际   idempotency_key='confirm:'+reservationNo
              有差额再写一条 REFUND amount=+差额  key='refunded:'+reservationNo
  reservation_line: confirmed_points / refunded_points 回填，status='CONFIRMED'
COMMIT
```

### 退回（失败 / 超时）

```
BEGIN
  reservation: HELD → REFUNDED, refunded_time=NOW()
  批次:    frozen -= P, remaining += P        （原路退回原批次，不改过期时间）
  account: frozen_balance -= P, balance += P, total_refunded += P
  points_log: REFUND amount=+P  key='refunded:'+reservationNo
COMMIT
```

## 五、⚠️ 最大的坑：他们也有一个过期回收器

`afv_billing_reservation` 上有 `idx_status_expire(status, expire_time, id)`，
admin 侧还有「只读查询过期占用扣费单」和「手动触发过期占用扣费单恢复」两个接口——
**说明 Java 那边有个定时任务在扫 HELD 单并解冻**。

现有单子的 `expire_time = create_time + 30 分钟`（实测 14:24:25 → 14:54:25）。
而我们的视频任务超时是 **40 分钟**（口播实测本地 GPU 出 15 秒视频要 14 分钟）。

照现状直接写：**任务还在跑，他们的回收器先把钱解冻了**；等我们任务成功去确认，
单子已经不是 HELD，确认失败——用户白嫖一次，或者我们重复扣一次。

两条都要做：
1. **我们写的单，`expire_time` 按任务类型给足**（视频 ≥ 60 分钟，图片/文案 10 分钟够）；
2. **我们自己的回收器只回收自己的**（`idempotency_key LIKE 'golife:%'`），
   并且要和他们确认：**他们的回收器要不要也按前缀跳过我们的单**。

第 2 条得他们配合，不是我们单方面能解决的。

## 六、上线方式：开关 + 影子模式

全部代码收在 `pkg/billing`，一个配置项 `Billing.Mode`：

| 值 | 行为 |
|---|---|
| `off` | 现在这样，完全不扣（默认） |
| `shadow` | 照常算价、记一条影子流水，**不动账**。用来和 Java 的 preview 对数 |
| `on` | 真扣 |

先用 `shadow` 跑一周，把我们算的价和 `quote/preview` 的返回逐条对；
对不上就报警，对得上再翻 `on`。不敢一步到位的原因在下一节。

## 七、这条路真实的代价（不粉饰）

1. **两套代码写同一批表**。他们改字段语义、加约束、改回收策略，都不会通知我们——
   和"自己验联盟临时 token"是同一类耦合，只是这次动的是**钱**。
2. **运营看不见我们**。计费驾驶舱、异常处理、补偿执行（`/admin/billing/compensations/execute`）
   全是 Java 的。我们写的单出问题，运营在他们后台看到的是来源不明的记录。
   要么我们补一套运营口，要么让他们的工具认 `golife:` 前缀。
3. **毛利对账会缺我们这块**。`reservation_line.cost_amount / cost_detail` 是给
   `/admin/margin/by-reservation` 用的，我们得填执行面的实际成本，否则报表里我们的单是空的。
4. **需要写权限**。现在服务账号对这几张表有没有 INSERT/UPDATE 要确认。

## 七点五、已经写好了（2026-09-27）

`pkg/billing` 按上面的方案实现完了，**默认 `Mode=off`，还没接进任何业务**：

| 文件 | 内容 |
|---|---|
| `billing.go` | 对外三个动作 Freeze / Confirm / Refund，加 Quote / Balance / Load；off-shadow-on 开关 |
| `price.go` | 算价：offer → variant → component → model_pricing |
| `ledger.go` | 账务事务：批次 FIFO、账户、账本、明细行 |
| `reclaim.go` | 过期回收器，只收 `golife:` 前缀的单 |
| `billing_real_test.go` | 连真库跑，8 个用例 |

测试连本地真实 `fusion_aigc` 跑（自己造配置和账户，跑完删干净，用户 ID 一律 999 开头），
**8 个用例全过**：

- 算价 + 冻结 + FIFO（先过期的批次先扣）+ 幂等（同 requestId 不重复扣）+ 确认
- 账本语义：CONSUME 的 `balance_after` 必须和 FREEZE 相同（钱在冻结那步就出余额了）
- 退回、重复退回幂等
- 部分成功：4 张扣 12、实际成功 3 张 → 扣 9 退 3，且 FREEZE = CONSUME + REFUND 配平
- ALL_OR_NOTHING 的档位即使传了实际量也全额扣（不自己放宽 Java 的语义）
- 余额不足：整笔回滚，连预留单都不留
- 回收器只收自己的单，Java 写的（`doubao:` 前缀）原样不动
- `Load`：模拟进程重启，只拿 userID + requestID 把单子捞回来结算

**每一步都顺带验账户与批次一致**（`SUM(batch.remaining) == account.balance`，
`SUM(batch.frozen) == account.frozen_balance`）——这是整套东西的底线，任何一步破坏它都算失败。

几个实现上的取舍：

1. **幂等靠唯一键冲突，不先查后写**。并发下"查空→双双插入"是真会发生的；
   直接插、撞 1062 再把原单读回来，才是安全的。
2. **账户用 `SELECT ... FOR UPDATE` 行锁**，不是读-改-重试的乐观锁。
   我们本来就在事务里、后面还要改批次，拿行锁更简单也不会活锁。
   `version` 照常 +1，保证 Java 那边的乐观锁检查仍然生效。
3. **批次的加锁顺序固定**（`expire_time` 升序、NULL 最后、再按 id），
   冻结和解冻用同一个顺序——否则和 Java 并发时会交叉锁批次而死锁。
4. **批次凑不齐就整笔回滚**。账户余额够但批次不够，说明两者已经不一致了；
   宁可报错让人来查，也不要扣一半把不一致扩散下去。
5. **算 0 点不写账**，也就不需要确认/退回，调用方拿到 `nil` 照常往下走。

## 八、结论与工作量

战略上是 Go 逐步换 Java，那自己写扣费**不是重复建设，是迁移的一部分**，这条路成立。
但建议分两步，别一次推到底：

- **第一步（现在能做）**：算价转发他们的 preview + 我们写账务动作，`shadow` 模式跑起来；
- **第二步（跑稳之后）**：再谈把 Java 那边对我们这些入口码的扣费下线，责任整体挪过来。

工作量：`pkg/billing` 已经写完（约 900 行含注释，8 个真库用例全过，见第七点五节）。
**还差的是接进业务**：各模块提交时 Freeze、轮询器成功时 Confirm、失败时 Refund，
以及那份配置数据。接线大约半天，配置数据得等产品/后端把入口码定下来。

**前置仍然是那张配置表**：`afv_billing_offer` 里我们 10 个 `entry_code` 一条都没有，
连已存在的 `actionTransfer` 也只有 offer、**没有 variant**（查过了，空的）。
没配好，preview 算不出价，自己写也没有单价可依。
